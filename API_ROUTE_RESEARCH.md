# Claude Code harness + OpenAI API route research

Checked 2026-10-30. This document evaluates the opt-in `claude-codex api` route. Claude Code stays the agent harness and owns its local tools, subagents, hooks, skills, MCP and terminal UI. Plain `claude-codex` continues to use the ChatGPT-plan Codex route. API billing starts only when the user configures a project key and makes an inference request.

## Decision

The strongest candidate for an API-key pilot is:

```text
Claude Code Anthropic Messages
  → private authenticated 127.0.0.1 endpoint
  → CLIProxyAPI `api-keys.codex` translator
  → official OpenAI `/v1/responses` with a project API key
  → GPT-6.1 Sol or GPT-6 Astra
```

The provider must be `api-keys.codex`, **not** CLIProxyAPI's generic `openai-compatibility` provider. The latter routes upstream through Chat Completions; the CLIProxyAPI maintainer confirmed this in [issue #6674](https://github.com/router-for-me/CLIProxyAPI/issues/6674). OpenAI says GPT-6.1 Sol and GPT-6 Astra need the [Responses API for tool calling](https://developers.openai.com/api/docs/guides/function-calling). A Chat Completions fallback would therefore fail the main Claude Code tool-use requirement.

Use a separate private API profile and a short-lived project key. Keep the existing subscription profile and API usage/accounting separate. The [ChatGPT subscriber API credit benefit](https://developers.openai.com/api/docs/guides/chatgpt-api-credits) covers eligible **Responses API** usage, including built-in tool charges, after it is claimed for the linked API organization. It does not raise ChatGPT/Codex plan quotas, and OpenAI explicitly excludes *Codex usage through API keys* from that benefit. This proposal calls the API directly for model inference; it is not Codex CLI API-key usage. Confirm the project credit balance and billing behavior before relying on the allowance.

## What the quality evidence actually says

Independent [FrontierCode 2.0](https://artificialanalysis.ai/evaluations/frontiercode-2-0) uses the same Stirrup agent harness for every model on 132 private real-repository tasks, three attempts per task. The current results include **GPT-6.1 Sol Max 40.6%, GPT-6 Astra Max 42.4%, Claude Fable 5.1 Max with fallback 31.6%, and Claude Opus 5.5 Max with fallback 46.4%** ([Sol/Fable comparison table](https://artificialanalysis.ai/models/releases/comparisons/gpt-6-1-sol-vs-claude-fable-5-1), [leaderboard](https://artificialanalysis.ai/evaluations/frontiercode-2-0)). Thus the OpenAI models are already competitive with or ahead of Fable on this coding benchmark, while Opus still leads. These are **model results in Stirrup**, not a measurement of this Claude Code bridge.

The broader [Artificial Analysis Intelligence Index v5](https://artificialanalysis.ai/articles/artificial-analysis-intelligence-index-v5) puts Opus 5.5 Max at 58, Astra Max at 57, and Sol 6.1 Max at 55. Those numbers combine coding with other kinds of work; they do not establish a universal ordering for this user's repositories. A [Gradle team's one-task field comparison](https://blog.gradle.org/two-agents-one-gradle-bug) found both Fable in Claude Code and Astra in Codex passed the task, while Fable's patch was the one they would merge. It also illustrates how tool palette and harness choices change the result. None of these studies tested **Claude Code → Anthropic translator → OpenAI Responses** directly.

The practical model policy to evaluate is Sol 6.1 `high` for ordinary coding, Sol 6.1 `max` for hard implementation, and Astra `max` for difficult architecture or review. This is a **test hypothesis**, not a promise that an effort label always improves a particular task. Compare against Opus 5.5 and Fable 5.1 on the same tasks and acceptance tests before claiming parity.

## Route capability and protocol checks

| Requirement | Evidence and remaining gate |
| --- | --- |
| Native OpenAI tool calling | The pinned CLIProxyAPI 8.0.46 `api-keys.codex` path sent a synthetic Anthropic tool request to `/v1/responses`, then converted the function call and matching result back into the next Responses input. The repeatable, credential-free `tests/smoke_api_contract.py` now uses the API profile's generated config against a loopback fake upstream. Real API inference remains untested. |
| Reasoning and privacy | The same protocol test saw `reasoning.effort=high`, `store=false`, and `include=["reasoning.encrypted_content"]`. OpenAI [recommends replaying reasoning items with function results](https://developers.openai.com/api/docs/guides/reasoning); the proxy's source has tests for encrypted reasoning replay, but this still needs a multi-turn live API check. `store=false` disables stored response objects; it is [not equivalent to Zero Data Retention](https://developers.openai.com/api/docs/guides/your-data). |
| Claude Code local tools | A real subscription-route smoke on Claude Code 2.1.312 invoked `Bash` in the main process and `Agent` then `Read` in a subagent. This tests the current bridge and mitigates concern from open [Claude Code issue #104309](https://github.com/anthropics/claude-code/issues/104309). Repeat on the API route and after Claude Code upgrades. |
| Search | The API contract test confirmed Anthropic `web_search_20260209` becomes OpenAI `web_search`. The existing subscription route exercised Claude Code WebSearch/WebFetch. Search on the direct API route still needs a real query, source verification and cost check. Claude Code's tool and OpenAI's hosted tool are different interfaces. |
| Images and other OpenAI tools | [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol) and [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) list image input and Responses tools including file search, image generation, computer use, hosted shell, MCP and tool search. Availability in the model API is not automatic exposure inside Claude Code. Each built-in tool needs an Anthropic-facing translation and its own action/result loop, or an explicitly installed local Claude Code MCP tool. |
| Streaming and tool search | The mock API-key route now checks **progressive SSE deltas before completion**, and the live subscription route returned 320 partial stream events in one Claude Code 2.1.314 run. See [STREAMING.md](STREAMING.md) for the distinction from WebSocket steering and GPT-Live. In pinned CLIProxyAPI source, `defer_loading` is stripped as it converts tools; a proposed full emulation in [PR #1892](https://github.com/router-for-me/CLIProxyAPI/pull/1892) closed without merging. Do not count OpenAI-native deferred tool search or its prompt-size benefit as verified. Test tool lists and tool-result round trips after every proxy or Claude Code update. |
| Context and model discovery | OpenAI's [API model pages](https://developers.openai.com/api/docs/models/gpt-6.1-sol) list **1,050,000** context for Sol/Astra; the current ChatGPT-plan route advertises 500k Sol and 272k Astra. A fake API-key profile with no override still advertised those subscription-sized values from CLIProxyAPI's built-in catalog. The official [List models API](https://developers.openai.com/api/reference/resources/models/methods/list) exposes IDs, but no context, effort or tool metadata. The new API profile intersects live IDs with the official documentation catalog, parses each model page, and supplies verified context/effort/search metadata. Unknown or unreachable model pages are omitted; if none remain, startup fails instead of inventing metadata. This discovery has a mocked test and live official-page parser checks, but no authenticated API-list check yet. |
| Prompt caching and effort changes | OpenAI [caches stable rendered prefixes automatically](https://developers.openai.com/api/docs/guides/prompt-caching), including tool definitions. Switching effort, tools or models can change that prefix. The current translator does not set a `prompt_cache_key`; OpenAI says it is optional for GPT-5.6 and later. Measure `cached_tokens`, cache writes, latency and total cost in real API calls instead of inferring efficiency from request shape. |
| Claude Code UI and plugins | Local [CLI, subagents, hooks, skills, commands, plugins and MCP](https://code.claude.com/docs/en/feature-availability) remain Claude Code capabilities. Model IDs and context/cost display need the existing picker and status-line adaptation. For an API route, the subscription-quota HUD fields must be replaced with **API** usage/spend data or hidden. Claude Code [turns off Remote Control and server-managed settings](https://code.claude.com/docs/en/feature-availability) with a custom `ANTHROPIC_BASE_URL`; a proxy cannot enable account-gated cloud features. |
| Windows | The current installer and service have native Windows CI. The fake API contract now runs on Windows CI too. Live Windows API-key inference, browser/desktop MCP permissions and plugin rendering still require a Windows machine test. |

The proxy's default behavior injected an `image_generation` tool even when the synthetic Claude Code request asked only for `Read`. Set `multimedia.disable-image-generation: "passthrough"` in the **API profile** so only the client's requested tools are forwarded; the mock test verifies this. Opt in to hosted image generation separately when its result path, user control and charges are verified.

## Community projects and maintenance evidence

| Project | Finding | Fit for this route |
| --- | --- | --- |
| [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) | Actively released; currently pinned here to v8.0.46 with verified release digests and private localhost authentication. Its Codex API-key provider uses native Responses. Two [high-severity advisories](https://github.com/router-for-me/CLIProxyAPI/security/advisories) published 2026-10-27 list affected versions no later than 8.0.44, so the current pin is outside their stated ranges. Translation still has open maintenance risk; a source pin is not a blanket security guarantee. | Best existing base for an isolated API pilot, subject to live and release regression gates. |
| [Claude Code Router](https://github.com/musistudio/claude-code-router) | Broad OpenAI Responses support and desktop/Windows UI, but its active issues report [lost `tool_result`](https://github.com/musistudio/claude-code-router/issues/1643), [reasoning stream block errors](https://github.com/musistudio/claude-code-router/issues/1725), and [missing context metadata in Claude Code](https://github.com/musistudio/claude-code-router/issues/1911). It includes many routing, logging, plugin and management features that widen the surface to audit. | Valuable implementation reference; these issues prevent treating its popularity as proof of complete compatibility. |
| [LiteLLM](https://docs.litellm.ai/docs/tutorials/claude_non_anthropic_models) | General gateway with Claude Code instructions, but its [compatibility matrix](https://docs.litellm.ai/docs/claude_code_compatibility) does not establish OpenAI-route coverage. More seriously, its own [security incident #47826](https://github.com/BerriAI/litellm/issues/47826) documents a compromised 1.107.0 PyPI release containing a credential stealer; the release was removed. | Do not install an unpinned package into a credential-rich local environment for this pilot. |
| [raine/claude-code-proxy](https://github.com/raine/claude-code-proxy) | Focused on ChatGPT subscription OAuth, not the direct OpenAI API project-key path. Its open [ToolSearch issue](https://github.com/raine/claude-code-proxy/issues/182) and [compaction issue](https://github.com/raine/claude-code-proxy/issues/163) need review. | Useful subscription-route comparison; cannot establish that Pro API credits or API-native tools work. |

Community reports and stars are discovery signals. A maintainer's open issue, source code and a reproducible request trace carry more weight than a launch post or a successful “hello world” screenshot.

## Safe pilot acceptance gates

1. Claim the [API credit benefit](https://developers.openai.com/api/docs/guides/chatgpt-api-credits) if eligible. Use a dedicated OpenAI project, an expiring project API key stored only in the local user secret store/private runtime, and a [hard spend limit](https://developers.openai.com/api/docs/guides/production-best-practices). Never put the key, prompt bodies or transcripts in this public repository or proxy logs.
2. Use the separate `claude-codex api` launch profile. It discovers available IDs via `/v1/models` and verifies model metadata against current official model pages before advertising a row in `/model` or computing compaction. Subscription OAuth, runtime state and quota HUD are isolated from the API profile.
3. Pass the fake upstream contract on macOS/Linux and Windows. Then make a small real API test that covers text, parallel function calls, tool result continuation, streaming, subagents, ToolSearch, WebSearch with citations, image input, structured output, interrupted requests and resumption. Inspect upstream paths and model IDs **without logging credentials or user content**.
4. Compare Sol/Astra and Opus/Fable on a small set of public or synthetic coding tasks **inside the same Claude Code release and with the same tools, permissions, time budget and tests**. Run repeated trials, count tasks that pass and patches a maintainer would merge, and record latency, OpenAI usage/cached tokens and actual API spend. Use a separate Codex CLI run only to measure the harness effect, not to claim direct model parity.
5. Only promote the API profile after the real capability matrix and spend/privacy behavior are measured. Re-run the checks when Claude Code, CLIProxyAPI or model catalogs change.

No live authenticated OpenAI API request or quality benchmark was run for this document: no project API key or confirmed claimed credit was supplied to this evaluation. The fake upstream verifies protocol wiring, not model intelligence or entitlement.
