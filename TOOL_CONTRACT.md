# Experimental tool-contract guard

The candidate in [tool-contract-guard-candidate.patch](upstream/patches/tool-contract-guard-candidate.patch)
is **not activated**, is not part of the selected runtime's source lock, and
does not establish full strict-tool support. The active backend and direct
legacy endpoint retain their existing behavior. No real account credential or
model inference was used in the tests below.

## Observed boundary

[Claude's tool reference](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-reference)
defines `strict`, `input_examples`, and caller restrictions as separate tool
properties. Its programmatic-only policy does not permit a normal direct tool
call. The public [OpenAI function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling)
describes `strict: true` and its schema requirements; it does not establish what
the private Codex subscription backend accepts or enforces.

In a synthetic Messages-to-Responses test against the currently selected Mac
translator, the adapter changed an explicit `strict: true` to `false` and
omitted an `input_examples` value. For a tool permitting only the synthetic
code-execution caller, it exposed the tool to the fake upstream and returned a
direct `tool_use` generated by that fake, both nonstreaming and streaming.
This is a protocol observation, not a real Claude Code permission-bypass
demonstration. It does not show that a user's session used these fields, that
Claude Code would execute the returned call, or that a real model would make
the call. The original pinned translator also returned the synthetic direct
call and changed strict mode; it forwarded the example field to the fake API,
which does not prove that a real API would accept the field.

An isolated [real Claude Code client fixture](tests/probe_tool_output_client.py)
adds an effect-level control. Its deliberately permissive synthetic
MCP server declares a string input but records a call even when the fake model
sends a number. The locked Claude Code 2.1.316 client passed that invalid number
to the synthetic server with a direct fake Messages endpoint, through the
locally selected translator, and through the isolated request-guard candidate.
For the candidate, a separate test-only loopback shim injected `strict: true`
into the outgoing synthetic tool definition; the fake Responses origin saw the
flag, but the invalid number still reached the synthetic MCP server. The
client itself had not sent that flag in the tested MCP request. In corresponding
controls, a valid string reached the fake server once, while an explicit
`PreToolUse` denial ran and prevented the invalid call from reaching it.
The selected installed translator was exercised locally on macOS; the direct
and candidate routes produced the same observations on [macOS, Linux and Windows](https://github.com/Jcstack/harnesslift/actions/runs/41521874679).

In another client test, the loopback shim injected a programmatic-only
`allowed_callers` field into the synthetic tool definition. The selected
translator omitted that field; the fake upstream then returned a direct call,
which reached the permissive synthetic MCP server. With the uninstalled
candidate, the client received an error, the shim observed HTTP 400, and no
request reached the fake upstream or fake tool. The client had not itself sent
the caller field in these samples. This confirms only the behavior of the
synthetic injection and controls, not a real model call, plugin invocation or
Claude permission bypass. The same baseline and combined-candidate controls
passed on [three platforms](https://github.com/Jcstack/harnesslift/actions/runs/41525145049).

This is evidence about a permissive fixture and the tested client/translator
combination, not evidence that a real provider violates strict mode, that a
real MCP server accepts invalid arguments, or that any user's tool was called.
Hook denial and schema validation are distinct controls. These local tests do
not establish behavior for other Claude Code versions, plugin permissions, or
programmatic caller policies.

The current schema normalizer can also drop an unsupported Unicode regex. With
`strict: true`, that changes the constraints that the original tool requested.
The existing ordinary best-effort path and its schema normalization remain
unchanged by the installed runtime. Avoid treating `strict: false`, an omitted
example, or a fake-successful tool call as proof of strict tool compliance.

## Separate caller-only candidate

The independently scoped [caller-policy patch](upstream/patches/caller-policy-guard-candidate.patch)
is also **not activated** or included in the runtime source lock. It rejects
programmatic-only, malformed and unknown caller policies before an upstream
request, while accepting an explicitly direct caller in the tested cases. It
does not implement programmatic execution: rejecting such a tool is a visible
compatibility limitation. Policy-bearing definitions are bounded to 4 MiB,
100,000 JSON tokens and 128 levels in this experiment; larger definitions and
unknown future caller names fail closed. Definitions without a caller-policy
field are not subject to those new fixture limits.

In isolated macOS controls, the native Codex executor returned request-scoped
400 errors without contacting its fake upstream for invalid policies in both
streaming and nonstreaming modes; a later direct request succeeded. The
preceding public-source baseline failed the six corresponding negative-control
checks. The locked real client also received a 400 before the fake upstream or
fake MCP tool in the injected programmatic-only case. A separate API fake and
dynamic-tool probe passed; three synthetic dynamic-tool stages preserved the
same prompt fields and session cache key versus the locally selected binary,
both without caller policies and with an explicit direct policy on every tool.
That comparison does not establish real provider cache hits.
The corresponding protocol, native-executor, real-client and synthetic
cache-structure controls without caller policies passed on [macOS, Linux and Windows](https://github.com/Jcstack/harnesslift/actions/runs/41526176567);
a later [three-platform comparison](https://github.com/Jcstack/harnesslift/actions/runs/41529298769)
also retained the prompt fields and cache key with an explicit direct policy,
using a candidate that combines this guard with the separate browser-state
experiment. No browser-state content appeared in that comparison.

An additional [handoff fixture](tests/probe_caller_handoff.py) used separate
baseline and candidate executables, a temporary TLS ingress and a fake origin.
On macOS, an admitted baseline stream completed after candidate publication;
the baseline forwarded a restricted request after dropping its field, the
candidate rejected it before the fake origin, and a later ordinary request
succeeded. The same temporary ingress and CA survived rollback, and a locked
Claude client continued its synthetic conversation across a subsequent
baseline-to-candidate handoff. The two fixture bundles use a mocked source
lock; this is not provenance verification or a live-session rollout test.
The same handoff and locked-client fixture also passed on [three platforms](https://github.com/Jcstack/harnesslift/actions/runs/41526902170).

This narrower candidate deliberately leaves the existing `strict: false`
translation and dropped `input_examples` unchanged. A fake invalid strict
argument still becomes a tool call, so it must not be marketed as strict-tool
support or complete caller-policy support. It requires actual plugin, provider
and broader safe-handoff acceptance before any rollout.

On this Mac, two short sequential 300 ms samples using a synthetic
1,000-message, 100-tool request measured 1.313–1.366 ms per conversion for
the baseline and 1.369–1.386 ms for the caller-only candidate when no policy
was supplied. With an explicit direct policy on every tool, the samples were
1.326–1.413 ms and 1.527–1.534 ms respectively. These non-randomized samples
are local translation measurements, not end-to-end or model latency.

## Isolated request guard

The candidate preserves an explicit `strict: true` only when the normalized
schema is structurally identical to the supplied one. If normalization changes
it, the candidate returns a request-scoped HTTP 400 before contacting the fake
upstream. It also rejects malformed, unknown, or programmatic-only caller
policies instead of exposing those tools for a direct call. A policy that
explicitly allows both direct and programmatic calling is allowed for direct
calls, but programmatic calling itself is not thereby implemented. Duplicate
keys and excessive JSON nesting in tool definitions with these properties are
rejected. Existing tool-removal and deferred-tool paths remain subject to their
separate acceptance gates.

The local [Messages fixture](tests/probe_tool_contract.py) passed the candidate's
limited preflight checks for nonstreaming and streaming requests. A separate
[native executor fixture](tests/native_tool_contract_fixture.go) used synthetic
credential-shaped metadata and a loopback fake: unchanged strict requests reached
the fake with the flag preserved; changed strict schemas and programmatic-only
tools failed before the fake in streaming and nonstreaming modes with a
request-scoped error; a subsequent valid synthetic request still worked. The
same native fixture failed against the preceding public-source baseline. These
results do not use an authenticated account or prove provider behavior.

**Release blocker:** a fake upstream that ignores `strict: true` can still send
arguments that do not match the input schema, and the candidate returns them
as a tool call. The candidate drops `input_examples`, and actual Codex backend
acceptance and enforcement are unverified. The current design must not be
described as strict-output validation, installed into a live session, or used
to claim complete caller-policy support. Safe completion requires validated
tool-name and session binding, bounded full-schema validation before any tool
effect, streaming/parallel and malformed-input tests, explicit handling of
examples and programmatic callers, and real client/provider acceptance.

Two maintained Go validation libraries merit investigation, not automatic
adoption. [santhosh-tekuri/jsonschema](https://github.com/santhosh-tekuri/jsonschema)
has open reports about [large-number resource consumption](https://github.com/santhosh-tekuri/jsonschema/issues/261)
and [deep-schema compilation cost](https://github.com/santhosh-tekuri/jsonschema/issues/266).
[google/jsonschema-go](https://github.com/google/jsonschema-go) has open reports
about [number handling](https://github.com/google/jsonschema-go/issues/80) and
[numeric const/enum precision](https://github.com/google/jsonschema-go/issues/83).
Those reports concern specific versions and inputs, not every use of either
library. Any candidate must disable uncontrolled external reference fetching,
bound time and memory, protect error contents, verify dialect and numeric
semantics, and pass positive and adversarial controls before adding a dependency.

A separate [validator fixture](tests/validator-fixture/validator_test.go) uses
`santhosh-tekuri/jsonschema` v6.0.3 with synthetic data only; it is a standalone
test module, not a production dependency or an output guard. It bounds fixture
input bytes, nesting, token count, number length and exponent before compiling
or validating; duplicate keys and external reference loading are rejected. A
large-integer const, local references and selected invalid arguments passed
their positive/negative controls. In this configuration, Draft 2020's default
format behavior accepted an invalid IPv4 string until format assertions were
explicitly enabled. An unknown format remained unenforced even with assertions,
so a production design needs an explicit format/dialect policy. These examples
do not establish bounded CPU or memory for every schema, streaming safety,
complete JSON Schema equivalence, or protection against every numeric edge.

Go's standard JSON decoder replaces a lone escaped surrogate with U+FFFD,
which can collapse two distinct serialized inputs before comparison. The
standalone fixture now refuses malformed UTF-8 and unpaired escaped surrogates
before decoding, while testing a valid pair, a literal replacement character,
and an escaped backslash as positive controls. This is a conservative fixture
policy, not complete Unicode or JSON dialect coverage and not an installed
runtime change.

The [selected public-suite fixture](tests/validator-fixture/conformance_test.go)
also runs 25 files from a [pinned JSON Schema Test Suite commit](https://github.com/json-schema-org/JSON-Schema-Test-Suite/tree/3f05891cac5d51ffa068d7076d1372130e00c829).
On macOS, Linux and Windows, 836 cases reached validation on each runner: none
were falsely accepted and 17 were falsely rejected against the suite's expected
results. All 17 concerned
`format` values: the fixture explicitly asserts formats, whereas those draft
2020-12 cases treat the format as an annotation by default. One additional
case was refused by the fixture's exponent limit before validation. This is a
deliberate fixture-policy comparison, not a claim that the library or the
suite is wrong. The selected cases omit many files, optional and remote-reference
scenarios; the separate regexp counterexample below demonstrates why the zero
false-acceptance count does not establish complete safety. The [full observation run](https://github.com/Jcstack/harnesslift/actions/runs/41522713263)
passed on all three platforms.

The default Go regexp engine adds another concrete incompatibility. In the
local fixture, the schema pattern `^.$` accepted a carriage return and the
Unicode line separator U+2028, while a Node ECMAScript Unicode-regexp control
rejected both and accepted a normal letter. JSON Schema describes its regex
syntax in terms of [ECMA 262](https://json-schema.org/understanding-json-schema/reference/regular_expressions),
whereas the [validator's default](https://pkg.go.dev/github.com/santhosh-tekuri/jsonschema/v6@v6.0.3#Compiler.UseRegexpEngine)
uses Go's regexp engine. This is a synthetic false-acceptance example, not a
complete regex conformance or security audit. A production guard must explicitly
resolve dialect fidelity and resource limits; simply enabling this fixture's
default validator is unsafe.

Using a backtracking engine also requires careful failure handling. The
validator's [custom-regexp example](https://github.com/santhosh-tekuri/jsonschema/blob/v6.0.3/example_regexp_test.go)
maps a matcher error to `false`. If a matcher is configured to time out, the
[regexp2 project](https://github.com/dlclark/regexp2/tree/v2.12.0) describes
timeout errors and backtracking behavior. A separate synthetic test shows why
mapping a hypothetical match error to `false` can falsely accept an input under
`not`: the failed match becomes a successful negation. That test does not run
regexp2 or demonstrate an actual timeout. A real adapter must propagate a
bounded, sanitized failure for the entire validation, and evaluate concurrency,
CPU and memory limits; a regex-engine swap alone is not sufficient.

An independent [synthetic subprocess fixture](tests/validator-fixture/worker_test.go)
tests one possible building block locally: per-call cancellation, a one-worker
concurrency gate, bounded request/response framing, fixed result categories,
and refusal of external schema references. A deliberately hanging child was
canceled after an explicit readiness signal, a waiting second call timed out,
and a later call reused the released slot; oversized synthetic output was
discarded. The process receives a minimal environment and test-only data; a
synthetic unrelated secret variable was not inherited in the control on [three platforms](https://github.com/Jcstack/harnesslift/actions/runs/41523801706).
This fixture has no hard memory or CPU quota, process-tree sandbox, production
protocol, streamed tool handling, or deployed integration; it does not solve
the known regex and format differences.

A separate [synthetic stream-gate fixture](tests/validator-fixture/stream_gate_test.go)
prototypes a narrower release rule: buffer at most eight synthetic function
calls, compare item/call identities and accumulated arguments against their
terminal counterparts, and validate every call before exposing any of them.
It accepts only a small object schema subset whose properties are all required
strings and whose additional properties are forbidden; schemas using patterns,
formats or other keywords are refused. Cases cover interleaved valid
calls, an invalid parallel call, missing or changed terminal data, duplicate
identities, late deltas, cancellation, an oversized argument and a different
request's call. The fixture and its worker passed a local Go race-detector run,
and the [validator-only gate](https://github.com/Jcstack/harnesslift/actions/runs/41524490404)
passed on three platforms.

This is an abstract, sequential event model: it does not parse actual Responses
or Messages streams, authenticate real session/tool identities, execute tools,
cover post-release cancellation or implement eager streaming. It has no CPU or
memory quota and is not activated. Its narrow schema subset is a temporary
fail-closed research constraint, not complete strict-tool compatibility.
The selected translator can close a completed function block on
`response.output_item.done` before `response.completed`; earlier real-client
synthetic tests also exercised a completed call followed by an incomplete
parallel call. See [streaming evidence](STREAMING.md#incomplete-tool-call-safety-2026-11-02).
Waiting for the terminal response would change that timing and needs explicit
latency, cancellation, tool-result and text-interleaving acceptance tests.

The fixture initially resolved `golang.org/x/text` v0.14.0, for which OSV
reported [GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970) and
[GO-2026-6629](https://pkg.go.dev/vuln/GO-2026-6629). It was repinned to
v0.42.0, already used by the reviewed upstream source. At this check, OSV
reported no matches for the resulting six public modules; that is not a
reachability analysis or proof of safety. The fixture's [offline checksum lock](tests/validator-fixture/go.sum)
and [public-module OSV check](tests/validator-fixture/audit.py) are separate
from the active runtime and send no user prompts or credentials.

The [manually dispatched workflow](.github/workflows/tool-contract-observation.yml)
builds the isolated candidate from pinned public source on macOS, Linux and
Windows. The [first three-platform observation](https://github.com/Jcstack/harnesslift/actions/runs/41519344980)
passed the preflight, native-executor and existing tool-contract checks; it did
not include the subsequently added standalone validator fixture. The [later
three-platform observation](https://github.com/Jcstack/harnesslift/actions/runs/41520836559)
also passed the separate validator fixture and its dependency checks. On all
three platforms, the fixture still observed an unknown format being accepted;
it did not include the subsequently added real-client MCP effect controls.
Passing the preflight gate does **not** remove the release blocker.
[A synthetic benchmark fixture](tests/tool_contract_benchmark.go) provides a
bounded starting point for measuring translation overhead; it is not an
end-to-end latency or model-quality benchmark.

On this Mac using Go 1.27.3, two short sequential 300 ms samples of a synthetic
1,000-message, 100-distinct-tool request measured 1.365–1.393 ms per conversion
before the candidate and 1.444–1.454 ms with it when tools omitted these policy
fields. When every tool explicitly specified a direct caller and nonstrict
mode, the samples were 1.413–1.416 ms before and 1.635–1.643 ms with the
candidate. The candidate's additional caller/schema scan was integrated into
the existing message traversal before this measurement. These small,
non-randomized local samples do not establish real workload or model latency.
