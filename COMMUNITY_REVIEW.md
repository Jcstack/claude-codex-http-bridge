# Community proxy review and upgrade gate

Checked 2026-10-30. This project keeps Claude Code as the harness. The current authenticated localhost service runs the reviewed CLIProxyAPI v8.0.46 release. No candidate below was given an OAuth credential in this review, and the live service was not replaced.

## Protocol finding

Claude Code can add a tool in a `role: "system"` message using `tool_addition`, or return `tool_reference` blocks after ToolSearch. The Claude API renders these at that position without rewriting the cached tool prefix. [Anthropic's mid-conversation tool guide](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages), [tool reference and caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-reference).

The current proxy strips `defer_loading` but forwards every deferred schema at request start. It also drops inline `tool_addition` and `tool_removal` changes. `tests/probe_proxy_features.py` sends four synthetic Anthropic Messages requests through a candidate binary to a loopback fake OpenAI Responses upstream. On the current pin it reports `false` for all four gates: inline tool addition, initial deferred-tool hiding, post-search reveal with a stable top-level tool list, and removal that constrains callable tools without rewriting that list. The probe contains no real credential or user conversation. Run it without `--report-only` to require all gates before promoting a candidate binary; CI uses `--report-only` to record the known gaps on the current release.

OpenAI's [API Tool Search guide](https://developers.openai.com/api/docs/guides/tools-tool-search) describes native `tool_search` with deferred tools. The separate [ChatGPT-plan preview limits](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) explicitly exclude Responses `tool_search` on that route, while allowing function/custom tools and `additional_tools` items. The subscription-route design therefore needs **client ToolSearch as a normal Claude Code tool**, then a cache-preserving `additional_tools` input item when the client returns a trusted `tool_reference`. A direct API-key route can be evaluated separately for native `tool_search` after the user enables it and live verification is authorized.

A feature checklist and a successful text/tool demo establish transport behavior, not model quality. See [the controlled harness and model comparisons](MODEL_HARNESS_EVIDENCE.md).

## Isolated implementation candidate

The candidate starts from the **same v8.0.46 source commit** as the installed release, [`9717e32`](https://github.com/router-for-me/CLIProxyAPI/commit/9717e325ba6ab2c7483ea93ccb5f2047eb2e7dd5). [The first patch](upstream/patches/12d97cf-inline-tools-backport.patch) backports only the Codex translator files from upstream's unreleased [`12d97cf` tool-addition change](https://github.com/router-for-me/CLIProxyAPI/commit/12d97cfe196be266b45f4f7e0cc394c9fdc2e099). [The second patch](upstream/patches/12d97cf-deferred-tools.patch) withholds `defer_loading` tools from top-level `tools`, then inserts their full sanitized schemas as an ordered `additional_tools` item after Claude Code's `tool_reference` result. It accepts references only when their result matches a prior `ToolSearch` call ID, and builds OpenAI function schemas from an allowlist so new Anthropic-only fields do not reach Responses. A later `tool_removal` applies a current-turn OpenAI `allowed_tools` restriction; prior tool declarations and reveals stay in the cached prefix. Forced calls to removed or unavailable tools fail closed with request-scoped HTTP 400 before any upstream call; they do not place the account in cooldown. Unknown removal references also fail closed. This covers function/tool references and mapped MCP function names, not every hosted-MCP-toolset lifecycle variant. Neither patch contains credentials.

The local isolated macOS build passed the Codex translator unit package, the fake OpenAI API function-call/stream contract, and all four `probe_proxy_features.py` gates. The [candidate workflow at commit `6b57b1b`](https://github.com/Jcstack/claude-codex-http-bridge/actions/runs/41030566455) passed all four gates, translator unit tests and the streaming/tool contract on macOS, Linux and native Windows without OAuth or API keys. The removal gate also verifies that a forced removed tool returns HTTP 400 without contacting the upstream. A separate [live subscription probe](tests/live_candidate_subscription.py) sent synthetic ToolSearch history through the candidate to the **existing authenticated localhost service**: GPT-6.1 Sol accepted the `additional_tools` reveal, called the loaded fixture tool, continued after its result, and respected a later `tool_removal`. A further isolated **real Claude Code** run called `ToolSearch`, then a temporary MCP fixture tool, and completed from its result. The candidate received only the existing service's private localhost client key; no OAuth file or OpenAI project key was copied to it. A subsequent [isolated coding pilot](HARNESS_PILOT.md) using candidate commit `383f3f2` passed a synthetic SSE repair task twice in Claude Code; the later `6b57b1b` change adds request-scoped policy errors and a no-removal fast path, and was validated by the cross-platform contract run above. The active service and installer still use the official v8.0.46 binary. Native Windows login, candidate-versus-pin workload comparison and longer real-project sessions remain unverified.

To repeat the live probe after reviewing a candidate binary, run `python3 tests/live_candidate_subscription.py /path/to/candidate --root /path/to/installed-bridge --claude-smoke`. It consumes a small amount of the existing subscription quota. The script prints only the model ID and pass/fail stages, then stops its temporary candidate process and removes the temporary local-key copy. Omit `--claude-smoke` to test the synthetic Anthropic Messages calls without launching Claude Code.

## Candidate acceptance sequence

1. Freeze an upstream source commit and its dependency lock. Apply only reviewed translation changes in an isolated build; keep real OAuth files outside the build environment. This is implemented for the v8.0.46 candidate above.
2. Run the synthetic probe on macOS/Linux and native Windows. Require the four tool gates plus tool-result pairing, parallel calls, long MCP names, unknown references, duplicates, streaming/non-streaming output and interrupted turns before promotion.
3. Confirm `additional_tools` is placed after the relevant ToolSearch result or system tool addition, with the original top-level `tools` prefix unchanged. Reject a candidate that merely drops `defer_loading` or echoes schema text while changing the leading tool list.
4. Compare the candidate against the current pin on the **same** small, isolated subscription task and model, recording request model, tool calls, result pairing, cache tokens, latency and success. Never print tokens or prompt bodies in CI or public logs.
5. Review transport, inbound authentication, permissions, release checksums and Windows binary provenance. Only then change the installed service after active/background sessions finish.
