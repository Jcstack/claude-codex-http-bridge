# Claude Code × Codex capability and reliability plan

Updated 2026-11-06 (Asia/Shanghai). Work is guided by the long-running session and its child-session records. Update the evidence, open problems, and next steps after each phase.

## Goals and boundaries

- Claude Code remains the harness and retains local commands, permissions, hooks, skills, MCP, plugins, plan mode, subagents, and background work.
- Use validated protocol adaptation and local tools to expose Codex/OpenAI reasoning, context, caching, search, vision, computer interaction, and streaming capabilities.
- Discover model lists, context limits, effort levels, and capabilities from the current account and upstream metadata; do not make historical model parameters permanent rules.
- Do not add useless content, weaken task quality, lower user-selected effort, or relax permissions to improve cache reuse.
- Keep raw logs, prompts, project paths, credentials, native compaction state, and runtime configuration on the local machine. The repository contains implementation, synthetic tests, and necessary findings only.
- Keep existing sessions working. Prepare and validate replacement translators before switching traffic, and allow old requests to drain. Killing the original listener is not a disruption-free restart.
- Leave the Project API route disabled. Do not invent Opus/Fable comparisons without a Claude account or equate credential-free CI with a real Windows account test.

## Method

Record the same evidence for each capability: user scenario, harness behavior, model/account/route, official references, community maintenance and issues, protocol tests, actual execution, privacy boundary, and known limitations.

Classify results as verified, adaptation needed, unverified, or blocked by an upstream or environmental prerequisite. HTTP 200, a similar model name, a listed tool, or one successful demonstration does not establish complete acceptance.

Start each iteration with read-only diagnostics of the tracked session and its children, then prioritize improvements relevant to real work. Distinguish request failures, interrupted SSE streams, expected test failures, application errors, and tool adaptation problems. Do not add records of the same request from two proxy layers together.

The tracked session's anonymous marker is stored locally in the private installation's `runtime-audit/target.json`, preventing temporary test sessions from being mistaken for it. That file is not committed.

## P0/P1 execution order

The 2026-11-06 inventory has 18 open P0 items and 11 open P1 items. Several
describe different acceptance gates for the same reliability work. They remain
open until their stated boundary is met; an unavailable host or provider
capability is not a successful test.

1. Diagnose the recurring incomplete-stream failure before expanding other
   features. Follow the current incident session and its children, preserve
   the former private audit target, and compare failed streams with completed
   controls. A bounded observer has now been activated for new managed requests;
   original-service and ingress migration remain separate work.
2. Establish recovery inside a verified account boundary, including OAuth
   refresh, selection changes, hosted tools, second-attempt error semantics,
   cancellation, concurrency and total memory. Keep the experimental replay
   disabled until these gates pass. A server timeout cannot be repaired by
   inventing a completion event or unconditionally repeating an action.
   Apply the reviewed [native retry requirements](COMMUNITY_REVIEW.md#native-codex-retry-decisions-2026-11-06):
   typed errors, an overall budget, absolute server deadlines, cancellation
   and bounded progress reporting. A notification or transport change must
   not restart the waiting period or bypass its deadline.
3. Complete cooperative listener/controller migration and login recovery.
   Existing direct clients and the current socket owner lack a demonstrated
   socket-transfer protocol. A real Mac reboot and authenticated Windows login
   require those environments and a safe opportunity; never reboot active work
   merely to check a box. Linux user-service support is a separate implementation.
4. Complete route-specific cache, context, compaction and HUD acceptance using
   synthetic histories and independent task outcomes. Retain unsupported cache
   controls, unknown quota/pricing and unavailable account entitlements as such.
   Include model/effort changes, dynamic tools, account isolation and resume/fork.
5. Validate catalog publication with account switching and current-client model
   settings. Treat startup-only settings and partial effort sets as explicit
   compatibility boundaries. The separately authorized Sign in with ChatGPT
   grant and the disabled paid Project API are not interchangeable with the
   existing Codex credential route.
